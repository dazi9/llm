# 第七章 数据决定行为:两个语料,两个模型

> 同一个架构、同一个训练循环、同一张显卡——唯一不同的是喂进去的语料。
> v1 吃童话故事,val 1.25,写出的故事有对话有结局;v2 吃真实网页,
> val 2.68,写出主题连贯的说明文。本章讲数据管线怎么搭、两次预处理
> 事故教会我们什么、以及"数据决定行为"这条深度学习第一定律的实证。

## 7.1 两个语料,两种人格

| | TinyStories (v1) | Fineweb-Edu (v2) |
|---|---|---|
| 文档数 | 2,119,489 个故事 | ~218 万网页 |
| 体量 | 1.92GB 纯文本 → 4.67 亿 token | 6.5GB → 29 亿 token |
| 平均文档 | ~220 token(短) | ~1300 token(长) |
| 词表 | 10,000(260MB 样本,20 秒) | 32,000(320MB 样本,18 分钟) |
| 训出的人格 | 童话腔:"Once upon a time…" | 说明文腔:"The history of…" |
| 验收 val | 1.2535 | 2.6755 |

**两个 val 不可互比**——语料不同、词表不同,perplexity 是语料内的量。
可比的是**行为**:给 v1 和 v2 同一个开头,v1 接童话,v2 接百科条目。
这就是"数据决定行为"的最小实证,也是数据配比实验(lab8)的出发点。

## 7.2 v1 管线:一条流水线与它的三个速度记录

TinyStories 是 txt 文件,管线在 `src/prepare_data.py`:

1. **BPE 训练**(`train_bpe`,250MB 样本):262MB → 10K 词表 **20 秒**
   (增量计数 + 惰性堆,见第二章)
2. **文档切分**:按 `<|endoftext|>` 分隔符切——注意要先在语料里
   **确认分隔符存在**(我们 `grep -c` 数过 2.2 万个,拍板了切分方案)
3. **多进程编码**(`encode_corpus`,33-57 行):`mp.Pool(20 workers)`,
   每个文档一个编码任务,主进程把结果流式追加进 uint16 bin
   ——**4.67 亿 token,30 秒**。三个速度记录的幕后都是同一个原则:
   **每个文档编一次,结果永远缓存;进程间只传 ID 不传字符串**。

uint16 的隐藏约束:词表必须 < 65536——这是选择 10K/32K 词表的
工程理由之一(32K 也恰好卡在 uint16 内,第九章会用到)。

## 7.3 v2 管线:当数据从"小甜点"变成"工业原料"

Fineweb-Edu 是 parquet 格式、文档长、体量大——同一套思路,
三个环节全部重写(`src/prepare_fineweb.py`):

1. **BPE 32K 重训**(320MB 样本,18 分钟):网页文本词表多样性
   远超童话,merge 难度高 10 倍;32K 词表换来 5.1 字符/token 的压缩率
2. **流式读取**(117 行):`ParquetFile.iter_batches(batch_size=2000)`
   ——内存里永远只有 2000 个文档,绝不整个 shard 进 RAM
   (第一版 `read_table` 全量加载直接 OOM,见 7.4)
3. **哈希切分**(108-111 行):对每个文档取 md5 前 4096 字节,
   `hash % 100 == 0` 进验证集——**确定性、可流式、无需先记住全集**

产出:29 亿 train token + 3040 万 valid, uint16 bin 5.8GB。

## 7.4 两次预处理事故(每夜一个,教训编入 HANDOVER)

**事故一:显存套娃**。第一版 v2 管线用 `mp.Pool.imap` 编码 71.8 万文档
——imap 会**急切地把整个可迭代对象 pickle 进队列**,主进程膨胀到
13GB,被 OOM 击杀(WSL 15GB 上限)。解法:窗口化提交——每次只
提交 8000 个文档,`pool.map` 阻塞等完再提交下一窗。

**事故二:worker 缓存炸弹**。窗口化后仍然 OOM:网页文本的唯一词
百万级,每个 worker 的分词缓存无限增长(6 worker × 数百 MB)。
解法:缓存 100 万条封顶(超限清空)+ 超长"词"(>5000 字节的
base64/压缩 JS)直接回退字节编码 + >200KB 文档直接丢弃。

事故后 v2 管线的内存曲线:从 15GB 顶格 → 2GB 平稳。**三次重启
换来的三条规则,全部进了 HANDOVER.md 第 2 节**——数据管线的
复杂度从来不在"把文本变 token",而在"资源边界与失败模式"。

## 7.5 预算算法:token 预算是怎么定的

训练前必须回答:"我有多少算力,该喂多少 token?"

```
可用时长 15h × 实测吞吐 33K tok/s = 17.8 亿 token 预算
→ batch 16 × 512 = 8192 token/步 → max_steps ≈ 120000
→ 相对语料的 epoch 数 = 17.8 亿 / 29 亿 ≈ 0.61(最终实际 0.34,见下)
```

v2 实际跑的是 9.83 亿 token(0.34 epoch)——因为中途为对齐额度
截止时间做了两次收缩(145K→105K→120K 步的重排,详见
reports/experiment-report.md)。**预算对齐比"把预算用满"重要**:
cosine 调度要求训练在预定的 max_steps 处恰好结束,提前掐断
= 没退火完 = 白跑。

## 7.7 踩坑记录

- **分隔符先验证再切**:TinyStories 的 `<|endoftext|>` 分隔符是
  `grep -c` 确认存在的,不是猜的——拍板前 30 秒的验证省掉一次全量重跑
- **uint16 上限**:词表 ≤ 65536 是 bin 格式的硬约束,32K 是刻意选择
- **下载校验**:hf-mirror 偶发返回 15 字节错误页且 curl 退出码为 0
  ——必须做 Content-Length 比对(本项目的下载脚本都带校验重试)
- **cron/自动化里的命令模板会过时**:工具参数一改,自动化模板就是
  踩坑源——HANDOVER 第 1 条的教训,本章再次应验
