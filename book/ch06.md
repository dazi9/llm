# 第六章 让它变快:bf16、FlashAttention 与编译

> 同一个模型、同一份数据、同一张显卡,吞吐可以从 **42,881 token/秒**
> 提升到 **155,656 token/秒(3.63 倍)**——本章讲这三层优化各自做了什么、
> 为什么有效、以及我们怎么知道它没把训练搞坏。这是全项目实验密度最高的一章,
> 所有数字都来自 `reports/benchmark.md` 的真实测量。

## 6.1 先想清楚:时间花在哪了

神经网络每一步 = 一串 GPU kernel(小函数)的接力。而 GPU 有两个特点:

1. **算得快,喂得慢**:算力(TFLOPS)远高于显存带宽(GB/s)。
   矩阵乘是"算力型",逐元素操作和 softmax 是"搬运型"
2. **启动有固定开销**:每发一个 kernel 都有微秒级的发射延迟

一个训练步 = 前向 + 反向 + 优化器,由几百个 kernel 组成。
**优化的本质:让大 kernel 干大活(融合),让 GPU 别闲着(重叠),
别让数据在显存和计算单元之间反复搬运(减少 IO)。**

## 6.2 第一层:精度(bf16)

fp32 每个 4 字节,bf16 只有 2 字节——显存减半、带宽需求减半、
Tensor Core 的吞吐翻倍,而数值上只是"少几位小数"。
训练对噪声的容忍度远比想象高:梯度本身就是统计信号,多出来的
几倍精度大多被优化器的随机性淹掉。bf16 对 fp16 还有一个决定性优势:
指数位多,**不需要 GradScaler** 这种防下溢的补丁。

实测(`reports/benchmark.md`,small 预设):fp32 51.6K → bf16 109.6K
tok/s(+112%)。唯一要小心的地方在第四章讲过:RMSNorm 的均值必须
在 fp32 里算(`src/model.py:50`),否则小值平方在 bf16 下蒸发。

## 6.3 第二层:FlashAttention——一次教科书级的 IO 优化

朴素注意力(`src/flash_attention.py:85-95`)有一个致命习惯:
它把 S×S 的分数矩阵完整写进显存,softmax 读一遍,backward 再读两遍。
序列长 S=512 时,这个矩阵是 batch×12头×512×512 的巨型中间产物。

FlashAttention 的洞察:**softmax 可以分块增量计算**。
数学核心是 online softmax——先看到一部分 key 时,维护"当前最大值 m"
和"部分和 l",看到新块时把旧结果按 exp(m_old - m_new) 重缩放。
我们的 Triton 实现(`src/flash_attention.py:18-82`)逐行对应这个思想:

- `m_i / l_i / acc` 三件套(47-49 行):运行最大值、运行和、加权累加器
- 重缩放(76 行):`acc = acc * alpha[:, None]`——新块的最大值更大时,
  旧贡献按比例缩小
- `exp2` 代替 `exp`(68 行):乘 log₂(e) 后用 exp2,Tensor Core 时代更快
- 防卫细节(67 行):整行被掩码时 m=-inf,用 `m_safe` 防止 inf-inf=NaN

结果:显存里**永远不出现** S×S 矩阵,IO 从 O(S²) 降到 O(S)。
实测:naive 2.45ms → sdpa(flash) 0.120ms → **我们手写的 Triton 版
0.113ms(57.1 TFLOPS,达 cuDNN 官方实现的 107%,naive 的 24 倍)**
—— `test_flash.py` 的对拍测试保证它数值正确。

## 6.4 第三层:torch.compile

PyTorch 默认执行是"看到一行,发一个 kernel"。torch.compile 用
AST 分析把整张计算图重新编排:逐元素操作串联融合、小矩阵乘合并、
内存分配复用。它对 `RMSNorm` 这种"5 个逐元素操作"的函数特别有效
——融合后只需读写一次显存。

规则:compile 后**无法归因**(你不知道哪个 kernel 慢),
所以我们的流程永远是——先 eager 冒烟验证数值,再开 compile 测吞吐
(`reports/benchmark.md` 全表就是这么测的),最后 compile 版 +30-40%
叠在前两层上,总计 **3.63 倍**,显存还省了一半。

## 6.5 优化器的账单(一个反直觉的发现)

你以为 kernel 才是瓶颈?`src/benchmark_adamw.py` 的微基准显示:
**我们手写的 Python 循环版 AdamW 一步要 23ms,占整个训练步的 ~29%**——
因为 134M 参数散在几百个张量里,每个张量若干 kernel,纯 launch 开销。
torch 的 fused 版把整个参数向量融成一个 kernel,占比降到 ~7%。
这个发现直接催生了 `train.py --optimizer fused` 开关:
**先测量,再优化**——本章的方法论比结论值钱。

```python
import sys, torch; sys.path.insert(0, "src")

q = torch.randn(8, 12, 512, 64, device="cuda", dtype=torch.bfloat16)
out_t = triton_attention(q, q, q)          # 我们的 kernel
out_s = torch.nn.functional.scaled_dot_product_attention(q, q, q, is_causal=True)
print((out_t.float() - out_s.float()).abs().max().item())  # ≈ 1e-2 内
```

## 6.7 踩坑记录(每条价值一次通宵)

- **冷启动读数是骗局**:开机首个 matmul "9 TFLOPS",稳态后 300+
  ——所有 benchmark 必须先 warmup(HANDOVER 之外的隐性第 14 条)
- **`tl.dot` 对 fp32 默认走 TF32**:和 fp32 参考对拍会有 ~3e-3 误差,
  不是 bug,容差要么放宽要么 `input_precision="ieee"`
- **kernel 内不能引用模块级普通变量**(Triton 3.5):`LOG2E` 必须内联
  或声明为 constexpr,否则 NameError
- **Triton 需要 gcc**:WSL Ubuntu 默认没有,`apt install gcc libc6-dev`
  (这是 env_setup 之外唯一的手工步骤)
- **WSL 侧 nvidia-smi 的频率读数不可信**:以 Windows 侧为准,
  实测 307MHz 假象骗过我们两次
