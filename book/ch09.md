# 第九章 部署:把模型装进 59MB

> 训练的终点不是"loss 停了",而是模型能被**拿走、装进别处、跑起来**。
> 本章记录本项目最惊心动魄的一段旅程:把我们手写的 134M 模型,
> 变成一个 59MB 的 GGUF 文件,在任何 x86 电脑上以 361.8 token/秒运行。
> 代码:`src/export_hf.py` + `reports/thin-laptop-guide.md`(实测数据)。

## 9.1 为什么不能"直接拿去用"

PyTorch checkpoint(`.pt`)是一份**绑定于本项目代码**的序列化:
张量名是我们自造的(`tok_emb.weight`)、架构假设写在我们的 `model.py` 里、
加载需要 `torch` 和我们的 import。要让它"独立",必须翻译成
**生态通用格式**——GGUF(llama.cpp 的标准),它自带元数据,
任何装了 llama.cpp 的机器都能运行,无需我们的代码。

但翻译有个前提:目标格式得"认识"我们的架构。幸运的是,我们的
架构选择(RMSNorm + RoPE + SwiGLU + 无 bias)正是 LLaMA 的配方
——翻译成 LLaMA 格式几乎是逐字段对应。**这就是架构选型的隐性红利:
选生态主流的配方,部署的路是现成的。**

## 9.2 翻译一:张量名(`src/export_hf.py:45-58`)

我们的命名(`blocks.3.attn.q.weight`)vs LLaMA 的命名
(`model.layers.3.self_attn.q_proj.weight`)——同一个张量,
两套名字。45-58 行的 rename_map 就是双语词典,逐层生成:

```python
rename_map[f"blocks.{i}.attn.q.weight"] = f"model.layers.{i}.self_attn.q_proj.weight"
rename_map[f"blocks.{i}.mlp.w1.weight"] = f"model.layers.{i}.mlp.gate_proj.weight"
```

(w1/w3 → gate/up 的对应关系就是 SwiGLU 的三矩阵结构,
第四章 4.3 的直觉在这里变成了一行映射表。)

**首跑就栽在这**:没做映射直接保存,llama.cpp 的转换器报
`Can not map tensor 'tok_emb.weight'`——错误信息直白,但前提是
你得先解决前面三层的依赖(见 9.5)。

## 9.3 翻译二:词表(整个项目最难的一次"自我转译")

llama.cpp 需要**标准格式**的词表描述,而我们的词表是手写的:
256 个字节 token + 9743 个 merge 产物。解法在
`src/make_tokenizer_json.py`:把我们的 merge 表翻译成
GPT-2 风格的 tokenizer.json:

1. **bytes_to_unicode 映射**(GPT-2 的经典处理):256 个字节值映射到
   "可打印 unicode 字符"——0x00 不是合法字符串内容,映射成 'Ā' 就合法了
2. **merge 表翻译**:每条字节对 `(a, b)` 写成 `"Ā Ā"` 这样的字符串
3. **预分词正则**:第二章那条 GPT-2 正则原样搬进 `pre_tokenizer.Split`

**验证的黄金标准**:`tokenizers` 库加载后,对测试句的编码结果
必须与我们的 `Tokenizer` **逐 id 一致**——
`make_tokenizer_json.py` 末尾内置了这个自检。词表翻译错一个字符,
生成出来就是乱码,这个自检不是可选项。

## 9.4 量化:536MB → 201MB → 59MB

- **f16 GGUF**(201MB):权重存成半精度——纯格式转换,零损失
- **Q4_0**(59MB):每个权重压成 4 bit + 一组共享缩放因子,
  模型体积缩到 1/9,质量损失在生成中肉眼难辨(llama-quantize 一步完成)

压测数据(5070 Ti Laptop 的 CPU,双通道):**361.8 token/秒**。
这就是"小模型"的部署自由:59MB 意味着它能装进任何设备——
轻薄本、旧笔电、树莓派、手机。**参数量的意义在部署时兑现为自由度。**

## 9.5 踩坑记录:一段真实的依赖链之旅

GGUF 转换本身 30 秒,通往它的路走了三小时——每一层错误都伪装成
更深层的问题(教科书级的"错误迁移"):

1. `convert_hf_to_gguf.py` 报缺 `transformers` → 装(清华源,1 分钟)
2. 报 `Can not map tensor` → 补张量名映射(9.2)
3. 报缺 `sentencepiece` → 装——但根因是它试图走 SPM 分支,
   因为 `tokenizer.json` 当时根本不存在(9.3 的脚本第一次跑就
   NameError 崩了,而且忘了重跑)
4. `tokenizers` 加载失败 → 逐字段排查,发现 `_PRETOKEN_RE` 引用写错
5. 全部修完后,转换器哈希匹配不到预分词器 → `get_vocab_base_pre`
   打一行补丁返回 "gpt-2"(我们的正则就是 GPT-2 的,已验证)

**方法论**:每一层只修一层,修完立刻重跑拿到下一层真实错误——
一次修三层的"聪明做法"会迷失在交叉症状里。

## 9.6 自己动手

**动手 1**:导出并转换(全链路 5 分钟):

```bash
python src/export_hf.py --ckpt ~/llm-lab/runs/main/model_final.pt \
    --out ~/llm-lab/export/v1
python src/make_tokenizer_json.py --ckpt ~/llm-lab/runs/main/model_final.pt \
    --out ~/llm-lab/export/v1
python ~/llm-lab/ref/llama.cpp/convert_hf_to_gguf.py \
    ~/llm-lab/export/v1 --outfile ~/llm-lab/export/v1-f16.gguf
```

**动手 2**:对比量化前后的输出:

```bash
llama-cli -m v1-f16.gguf -p "Once upon a time" -n 150 --temp 0.8
llama-cli -m v1-q4_0.gguf -p "Once upon a time" -n 150 --temp 0.8
# 两段故事不会逐字相同(采样随机),但风格、语法、连贯度应完全同级
```

## 9.7 踩坑记录

- **v2 的 QK-Norm 不可直转**:LLaMA 格式不认 qk-norm 张量,导出脚本
  会打警告。两条出路:手写 GGUF 的 qk-norm 映射,或重训无 qk-norm 变体
- **`tokenizers` 库的报错是嵌套的**:AutoTokenizer 失败只说
  "Couldn't instantiate",真实原因要用 `Tokenizer.from_file` 直接探
- **新版转换器改名了**:`convert_hf_to_gguf.py`(旧的 convert_hf_to_llama.py
  已被替代);且 C++ 侧 pre-tokenizer 名是 `gpt-2` 不是 `gpt2`——
  新旧命名不一致是 llama.cpp 重构期的真实状态,卡了我们半小时
