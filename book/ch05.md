## 5.1 交叉熵:把"猜错"变成一个数

模型输出的是 32,000 个 token 各自的分数(logits)。交叉熵做两件事:
先用 softmax 把分数变成合法的概率分布,再取"正确答案"对应的那个概率,
算 `-log(p)`——p=1 时 loss=0,p 接近 0 时 loss 飙向天文数字。

我们的手写版(`src/nn_utils.py:12-32`)不走 softmax,而是直接:

```python
m = logits.max(dim=-1, keepdim=True).values
lse = (logits - m).exp().sum(dim=-1, keepdim=True).log() + m
picked = logits.gather(-1, targets.unsqueeze(-1)).squeeze(-1)
return (lse.squeeze(-1) - picked).mean()
```

先减最大值 m 再做 exp——**数值稳定的 log-sum-exp**。32,000 个候选里
随便一个上溢成 inf,整个训练就报废,这个减法是保险丝。
`gather(-1, targets...)` 是"取出正确答案那个 logit"的向量写法。
`ignore_index=-100`(SFT 章会用)在 gather **之前**把掩码位置剔掉——
这个顺序是本周最贵的一课:顺序反了,gather 会对 -100 索引断言,
毒化 CUDA 上下文,然后在八竿子打不着的 backward 里报 CUBLAS 错误
(HANDOVER 第 12 条)。

**自己动手 1**:感受 log 尺度(这是读懂 loss 曲线的钥匙):

```python
import math
print(math.log(32000))    # 10.37 —— 瞎猜的起点
print(math.log(15))       # 2.71  —— 我们 v2 的终点,≈ 每 15 选 1
print(math.exp(-1.0))     # 0.37  —— loss 每降 1,正确率翻 e 倍
```

## 5.2 AdamW:不只是"沿梯度走"

朴素梯度下降是"往坡下走"。AdamW 加了三样东西
(`src/nn_utils.py:70-84`,与 torch.optim.AdamW 逐位对拍通过):

1. **动量 m**(70-77 行):梯度的滑动平均——在峡谷里不左右乱撞
2. **自适应步长 v**(78 行):梯度平方的滑动平均——梯度一直很大的参数
   走小步,一直很小的走大步
3. **解耦权重衰减**(`p.mul_(1 - self.lr * self.wd)`,83 行):每步把参数
   向 0 微缩,但**不**把这缩量算进梯度——这是与 Adam 的本质区别,
   也是 W 的由来(decoupled weight Decay)

实现注意:除以 bias correction(1-βᵗ)放在哪个变量上、`p.mul_` 与
`addcdiv_` 的先后顺序,都做过与 torch 的**逐位对拍测试**
(`test_adamw_matches_torch`,atol 1e-6)——顺序不同结果不同,
这是手写优化器的隐藏深坑。

代价也要知道:每个参数要配 m、v 两份状态(fp32),100M 参数 = 800MB
额外显存。我们的 benchmark(`reports/benchmark.md`)显示手写 Python
循环版的 optimizer step 占了整个训练步的 ~29%——教学版换执行速度,
这是本章最诚实的注脚。

## 5.3 学习率调度:先热身,再退火

`cosine_lr_schedule`(`src/nn_utils.py:45-55`)三段式:

- **warmup**(线性升到 α_max):初始参数是随机的,大学习率会把第一步
  就带偏到无法挽回的地方——先小步探路
- **cosine 退火**(降到 α_min):训练后期参数已在好解附近,大步会
  在解周围震荡出毛刺——逐渐减速"稳稳停下"
- **收尾保持**:超过总步数后锁定 α_min

为什么选择 cosine 而不是线性衰减?没有压倒性理论,是社区的
经验共识(LLaMA、GPT-3 同款)。我们的训练日志里能看到它的形状:
v2 从 lr 3e-4 平滑滑到 3e-5,loss 曲线在退火尾段下降得特别顺。

## 5.4 训练循环全景(`src/train.py:145-200`)

一个 step 的完整生命周期:

```
取批(数据.py 的 memmap 随机窗口)
→ autocast bf16 前向(117 行)
→ 手写交叉熵算 loss
→ loss.backward()(160 行,梯度出现在每个参数的 .grad 里)
→ gradient_clipping(164 行,全局 L2 范数超 1.0 就整体缩放——防梯度爆炸)
→ opt.step()(167 行,AdamW 更新)
→ 每 500 步:evaluate() 在验证集上算 val_loss(122-141 行)
→ 每 4000 步:torch.save 存 checkpoint(模型+优化器状态+步数)
```

**读日志的功夫**(每列都对应 CSV 的一行):

- `loss`(训练批):毛刺大是正常的;**持续上升**才是事故
- `val_loss`(评估批):这才是模型的真成绩。val 升 + train 降 = 过拟合
- `tok/s`:吞吐,EMA 平滑过;突降 1/4 且功耗腰斩 = 显存溢出(见 HANDOVER 第 3 条)
- `mem_gb`:峰值显存;贴着 12GB 跑就是踩在共享内存溢出的悬崖边
