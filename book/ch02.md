## 2.1 直觉:语言模型需要一本怎样的字典

第一章说过,模型的输出是"下一个字的概率分布"。但"字"是什么?

- **按字符**:英文 26 个字母 + 标点。字典小,但 "artificial" 要拆成 10 步,
  每一步都在浪费模型 precious 的注意力
- **按单词**:字典无限大(新词、错拼、任何语言……),永远列不全
- **字节级 BPE**:先按 256 个字节打底(任何文本都是字节!),再把语料中
  **高频共现的字节对**逐步合并成新 token——高频词变成 1 个 token,
  低频词自然退化成多个字节

这就是 Byte-Pair Encoding(BPE)。它的美妙之处在于**自适应**:给童话语料,
它学会 "Lily"、"princess";给代码语料,它学会 "def"、"self"。
本项目两套词表就是这么来的:10K(TinyStories)和 32K(Fineweb)。

## 2.2 预分词:先切,再合

BPE 有个致命的坑:如果允许跨词合并,"the" 和 "theater" 的 "the" 会是
两个不同 token——同一个字符串在不同上下文里变成不同 ID,模型直接疯掉。

解法:先用一条正则把文本切成"词",merge 永远不跨过切分边界
(`src/tokenizer.py:17-20`):

```python
GPT2_SPLIT_PATTERN = (
    r"""'(?:[sdmt]|ll|ve|re)| ?[A-Za-z]+| ?[0-9]+| ?[^\sA-Za-z0-9]+|\s+(?!\S)|\s+"""
)
_PRETOKEN_RE = re.compile(GPT2_SPLIT_PATTERN)
```

这条 GPT-2 同款正则值得逐段读:`'(?:[sdmt]|ll|ve|re)` 把 "it's" 的 "'s"
单独成词;" ?[A-Za-z]+" 让**空格跟随它后面的词**(所以 " the" 是一个 token);
`\s+(?!\S)` 处理句尾空白。这不是我们发明的——这是 GPT-2 的原始正则,
2020 年以来所有 GPT 系模型都在用它,历史包袱和兼容性都在里面。

**自己动手 1**:打开 Python,验证空格归属:


## 2.3 训练:数对、合并、再来一次

`train_bpe()`(`src/tokenizer.py:37`)的全部逻辑只有五步:

1. **预分词计数**(50-53 行):正则切词,统计每个词出现次数——注意立刻
   `encode("utf-8")` 转成字节,后面全程在字节世界工作
2. **初始化**(58 行附近):每个词 = 一串 0-255 的字节 ID;相邻字节对
   构成 `pair_counts`(总频次)和 `pair_to_words`(哪些词包含这个对)
3. **主循环**(71 行):`while len(merges) < n_merges and heap:`——
   每轮弹出频次最高的 pair,给它发一个新 ID(256 + 已有 merge 数)
4. **只重算受影响的词**(76-92 行):`pair_to_words[pair]` 告诉我们哪些词
   含有被合并的 pair——其他几十万个词碰都不碰。每个受影响词:先把它贡献的
   旧 pair 计数全部退回,合并,再把新 pair 计数加上、索引更新、新计数压堆
5. **惰性堆**(72-74 行):堆里可能有过期条目(计数已被后续合并改掉),
   弹出时校验 `pair_counts.get(pair, 0) != -negc` 就跳过

第 4、5 步是整个文件的性能心脏。朴素实现每轮全表扫描,10K 词表要几十分钟;
这个实现 262MB 语料 **20 秒**跑完(HANDOVER 之外,这是本项目第二骄傲的速度记录)。

## 2.4 惰性堆:一个值得背下来的工程模式

为什么不每次循环都全表 `max()`?因为那要扫几十万个 pair × 1 万轮。
但直接用堆又有新问题:合并会不断改 pair 的计数,堆里的旧条目全错了。

解法是**懒删除**(lazy deletion):计数更新时无条件压一条新记录进堆;
弹出时检查"这条记录的计数是否还等于当前计数",不等就扔。
堆里会积累垃圾条目,但垃圾不影响正确性——**校验代替修复**,
省掉每次更新的删除开销。这个模式在 Dijkstra 惰性堆、事件调度器里反复出现。

## 2.5 编码与"半词"之谜

训练得到的 `Tokenizer`(`src/tokenizer.py:105`)编码一个新词时
(`_bpe_word`,125 行):从字节序列开始,**反复找 rank 最小的相邻对合并**
——rank 就是 merge 的先后顺序。这也解释了那个经典谜题:

> 为什么 GPT 系 tokenizer 有 " artif" 这种 token,却还会输出 " artific" + "ial"?

因为编码时永远合并**当前词内 rank 最小**的对,而 rank 是训练语料的频次序——
模型输出的 token 序列可以事后看是"次优切分"。这不是 bug,是 BPE 的本性。

**自己动手 2**:亲手观察半词:


## 2.6 三个工程坑(全部真实踩过)

1. **无界缓存**(145 行):网页语料的唯一词是百万级的,per-worker 分词缓存
   无限增长会把 WSL 的 15GB 内存吃穿(第 6.1 节 OOM 事故)。
   解法:超过 100 万条就整体清空——热词很快会再进来。
2. **巨型"词"**(129 行):网页里有几 MB 长的 base64 串,正则会把它切成
   一个"词",BPE 合并循环 O(n²) 直接爆炸。解法:>5000 字节直接回退字节编码。
3. **特殊 token 要先剥离**(43-45 行):`<|endoftext|>` 若混进训练文本,
   会被切碎成多个普通 token——先按特殊串切开再计数。

每一条在 `HANDOVER.md` 的调试手册里都有对应条目——**分词器是全项目
事故密度最高的文件**,也是工程含量最高的文件。
